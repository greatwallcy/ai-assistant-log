### 13. MG90 vs MG90S vs SG92R 对比
**用户**: MG90为金属数字舵机，MG90S为模拟舵机，程序控制上有啥区别？SG92R和SG90有什么区别？

**AI**: 详细对比：
- **MG90**（金属数字）：有微处理器，一次PWM锁位，堵转保护，待机电流稍高

### 14. MCU跑飞问题全面排查
**用户**: 抓取波形发现语音模块有数据发出且正确，但单片机没信号给MP3，舵机也没反应。怀疑单片机跑飞，要加看门狗

**AI**: 从GitHub拉取全部源代码，逐文件审查，发现4个致命问题：

**问题1（致命）**：中断中调用OLED I2C操作
- USART1_IRQHandler中调用Face_Config()→OLED_Clear()+OLED_Update()
- 软件I2C位操作（PB8/PB9开漏）被中断抢占后总线状态混乱→HardFault→MCU死机
- 这是偶发性通讯异常的根因

**问题2（致命）**：USART1_DR重复读取
- USART_ReceiveData()先读一次存到变量，然后if-else链中又多次读取
- DR读一次清空，后续全部返回0x00→只有0x29能匹配，其他语音指令全部失效

**问题3（致命）**：MP3队列从不处理+发送被注释
- main.c的while(1)中从未调用Serial_ProcessQueue()
- 19个music_*函数中Serial_SendMP3CmdToQueue()被注释或缺失
- MP3指令只拷贝到缓存不入队→单片机完全不给MP3发信号

**问题4（中等）**：无看门狗保护
- stm32f10x_iwdg.c存在但从未使用，MCU跑飞后无法自动恢复

**AI修复方案**：
- BlueTooth.c重写：中断中只读一次DR，switch替代39层if-else，中断中不调用OLED
- BlueTooth.h新增BlueTooth_ProcessPending()声明
- main.c添加IWDG看门狗+Serial_ProcessQueue调用+BlueTooth_ProcessPending调用
- PetAction.c所有music函数添加Serial_SendMP3CmdToQueue()
- 上传修复文件到GitHub fix/目录

## 技术要点
- GitHub REST API 可直接创建/更新文件，无需 git clone
- SG90烧毁主因：塑料齿轮打齿→卡死→电流飙升，金属齿轮舵机(MG90/DS041MG)可解决
- 数字舵机vs模拟舵机：PWM信号完全一样，区别在内部电路（数字舵机有堵转保护）
- STM32 USART_DR 读一次清空RXNE，不能重复读取
- 软件I2C（开漏GPIO位操作）不能在中断中调用，会导致总线状态竞争
- 独立看门狗(IWDG)：LSI约40kHz，预分频256，重装值625 → 超时约4秒
- MP3队列：环形缓冲144字节，中断安全入队，主循环出队发送
- MP3421输出1.5-2A不够，MP3423输出3A+可覆盖4路舵机堵转电流
- MG90（金属数字舵机）替代SG90：同尺寸兼容，有堵转保护，推荐首选
