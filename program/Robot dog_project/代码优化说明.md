## 优化日期：2026-04-16（第二轮全面审查）

---

## 一、致命BUG修复（会导致MCU死机）

### 1. 🔴 中断中调用OLED I2C操作 → HardFault死机
- **文件**：`BlueTooth.c` → `USART1_IRQHandler()`、`USART3_IRQHandler()`
- **问题**：语音/蓝牙中断中直接调用 `Face_Config()` → `OLED_Clear()` + `OLED_Update()`，内部执行软件I2C位操作（PB8/PB9开漏输出）
- **机理**：主循环正在执行动作（Servo_Angle等），I2C总线可能正在被主循环使用。中断抢占后重新操作I2C → 总线状态混乱 → SDA被锁死 → 下次I2C操作触发BusFault/HardFault → MCU进入 `while(1)` 死循环 → 完全无响应
- **症状**：偶发性通讯异常，语音模块有数据发出但单片机无响应，舵机不动
- **修复**：
  - 中断中只设置 `OLED_NeedUpdate` 标志位 + 存储 `Pending_Face_Mode` / `Pending_Action_Mode`
  - 新增 `BlueTooth_ProcessPending()` 函数，在主循环中安全执行 OLED 更新
  - 中断中不再直接操作任何 I2C 外设
- **修复文件**：`BlueTooth.c`、`BlueTooth.h`、`main.c`

### 2. 🔴 USART数据寄存器重复读取 → 语音指令丢失
- **文件**：`BlueTooth.c` → `USART1_IRQHandler()`
- **问题**：先 `USART1_RxData = USART_ReceiveData(USART1)` 读取并消费数据，然后在 if-else 链中又多次调用 `USART_ReceiveData(USART1)` 做比较
- **机理**：STM32F103 的 USART_DR **读一次就清空RXNE标志**。第一次读完后，后续所有 `USART_ReceiveData()` 返回 0x00
- **结果**：只有 `if(USART_ReceiveData()==0x29)` 能匹配（0x29比较0x00=false），所有其他语音指令全部失效
- **修复**：
  - 读一次存到局部变量 `uint8_t rxData = USART_ReceiveData(USART1)`
  - 后续用 `rxData` 做 switch-case 判断
  - 用 `switch` 替代 39 层 if-else，更清晰高效
- **修复文件**：`BlueTooth.c`

### 3. 🔴 MP3队列不处理 + 发送被注释 → MP3无输出
- **文件**：`main.c`、`PetAction.c`
- **问题1**：`main.c` 的 `while(1)` 中从未调用 `Serial_ProcessQueue()`，队列数据堆积不发送
- **问题2**：19个 `music_*` 函数中，`Serial_SetMP3Cmd()` 后面的 `Serial_SendMP3CmdToQueue()` 被注释掉或缺失，MP3指令只拷贝到缓存但不入队
- **结果**：单片机完全不向MP3模块发送任何指令
- **修复**：
  - `main.c` 主循环中添加 `Serial_ProcessQueue()` 调用
  - `PetAction.c` 所有 `music_*` 函数中添加 `Serial_SendMP3CmdToQueue()`
- **修复文件**：`main.c`、`PetAction.c`

### 4. 🔴 无看门狗保护 → MCU跑飞后无法恢复
- **文件**：`main.c`
- **问题**：`stm32f10x_iwdg.c` 存在但从未使用。MCU 跑飞后只能靠断电重启
- **修复**：
  - 添加 `IWDG_Init()` 初始化独立看门狗，超时约 4 秒
  - 主循环每次迭代调用 `IWDG_ReloadCounter()` 喂狗
  - MCU 死锁后 4 秒自动复位
- **修复文件**：`main.c`

## 三、代码架构优化

### 9. 中断处理函数重构
- **原方案**：中断中直接调用 `Face_Config()`（OLED操作）+ 39层 if-else
- **新方案**：
  - 中断中只做数据接收和标志设置（极短执行时间 <10μs）
  - `switch-case` 替代 `if-else` 链
  - 统一的 `Process_Voice_Command()` / `Process_BT_Command()` 处理函数
  - 主循环中 `BlueTooth_ProcessPending()` 执行OLED更新
- **优势**：中断响应时间从 ms 级降到 μs 级，消除了I2C竞争

### 10. 主循环结构优化
```c
while(1)
{
    IWDG_ReloadCounter();          // ★ 喂看门狗
    BlueTooth_ProcessPending();    // ★ 处理中断积攒的OLED更新
    Serial_ProcessQueue();         // ★ 处理MP3队列发送
    
    if(Action_Mode==0) ...         // 动作分发
    else if(Action_Mode==39) ...
}
```

## 六、MP3队列系统说明

```
┌─────────────┐    入队    ┌──────────────┐   出队+发送   ┌──────────┐
│ music_* 函数 │ ────────→ │  环形队列     │ ───────────→ │ USART2   │
│ SetMP3Cmd()  │           │  uart2Queue  │  ProcessQueue │ → MP3模块│
│ Enqueue()    │           │  144字节     │               │          │
└─────────────┘           └──────────────┘               └──────────┘
      ↑                        ↑                              ↑
  中断安全                    主循环调用                    阻塞发送
  (关中断入队)              (每轮循环处理)                (单字节等待TXE)
```

- 队列大小：144字节（18条指令 × 8字节/条）
- 入队：中断安全（`__set_PRIMASK(1)` 关中断保护）
- 出队：主循环中 `Serial_ProcessQueue()` 逐字节发送
- USART2 配置：9600bps，仅发送模式

## 七、待优化项（后续版本）

### 高优先级
1. **Action_Mode 边界检查**：`main.c` 中 if-else 链前添加范围检查
   ```c
   if (Action_Mode > 39) Action_Mode = 2;  // 超范围回到站立
   ```

2. **USART2 使能接收**：如果需要MP3模块回传数据，需要将 `USART_Mode_Tx` 改为 `USART_Mode_Rx | USART_Mode_Tx`

3. **音乐函数 static 变量**：`ci_fuzhi` 用法不统一，建议改为全局标志

### 中优先级
4. **TIM3_IRQHandler 清理**：当前中断中只有清标志位，可以考虑禁用TIM3更新中断（节省中断开销）

5. **Delay_ms 精度**：SysTick 延时会被其他中断打断，对精确时序有影响。可考虑改用 TIM 中断做非阻塞延时

6. **栈空间检查**：默认4KB栈，`OLED_Printf` 局部数组256字节。确保调用深度不超限

### 低优先级
7. **代码精简**：`stm32f10x_conf.h` 包含了所有外设头文件，可根据实际使用裁剪
8. **OLED 亮度调节**：当前对比度固定为 0xCF，可添加调节功能

## 八、硬件建议（配合软件优化）

1. **舵机保护**：每路串联 PTC 自恢复保险丝（0.5-0.75A）
2. **电源滤波**：MP3423 输出端加大电容（100μF+），吸收电流尖峰
3. **I2C上拉电阻**：PB8/PB9 外部接 4.7kΩ 上拉电阻到 3.3V（开漏模式必须）
4. **电源去耦**：STM32 VDD/VSS 旁路 100nF 瓷片电容，靠近芯片引脚
